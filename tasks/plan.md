# План реализации: Datamatrix Notepad

Статус: утверждено пользователем

Основание: утверждённая [спецификация](../docs/spec.md)

## 1. Обзор

Проект реализуется как статическое Blazor WebAssembly-приложение для desktop Chrome/Edge. Работа разбита на небольшие вертикальные срезы: сначала проверяется главный технический риск Web Serial, затем появляется надёжно сохраняемый блокнот, после этого сканирование связывается с активной заметкой, добавляются экспорт, финальная обработка ошибок и публикация на GitHub Pages.

До утверждения этого плана прикладной код не изменяется.

## 2. Архитектурные решения

### 2.1 Последовательный порт

- Один выбранный `SerialPort` принадлежит JavaScript ES-модулю `wwwroot/js/serial.js`.
- JavaScript отвечает за проверку `navigator.serial`, системный выбор порта, `open`, поток чтения, streaming-декодирование выбранной UTF-8 или UTF-16BE кодировки, закрытие и преобразование браузерных исключений в безопасные данные об ошибках.
- C#-сервис отвечает за состояние соединения, диагностические события и передачу текстовых фрагментов в `ScanFrameParser`.
- `ScanFrameParser` является чистым C#-типом: он хранит незавершённый буфер и выдаёт только полностью завершённые коды.
- Подключён одновременно только один порт. Диагностический лог показывает только его данные.
- Ссылка на объект `SerialPort` не сериализуется. Сохраняются только псевдоним, VID/PID и параметры соединения.
- При восстановлении приложение автоматически использует ранее разрешённый порт только при единственном однозначном совпадении; иначе предлагает выбрать порт вручную.

### 2.2 Состояние приложения

- Scoped-сервис `AppStateService` является единственным владельцем текущего `AppState`.
- В Blazor WebAssembly scoped-сервис живёт в рамках вкладки приложения и подходит для общего состояния страниц.
- Состояние хранится целиком под ключом `datamatrix-notepad.state.v1`.
- C# сериализует версионированное состояние. JavaScript-модуль хранения принимает последнее JSON-значение, выполняет debounce 300 мс и синхронно сбрасывает ожидающее значение при `pagehide`.
- Создание и удаление заметки требуют немедленного сохранения без debounce.
- Повреждённое или неизвестное состояние не перезаписывается автоматически.

### 2.3 Страницы и события

- `Home.razor` подписывается на завершённые коды только пока открыта главная страница.
- `Settings.razor` подписывается на сырые диагностические события и не добавляет тестовые сканы в заметки.
- Сервис порта сохраняет соединение при внутренней навигации между страницами.
- Компоненты отписываются от событий при уничтожении, чтобы исключить дублирующие обработчики.

### 2.4 Экспорт

- Чистый C#-сервис вычисляет имя и полностью покрывается модульными тестами.
- Отдельный JS-модуль создаёт `Blob` с MIME-типом `text/plain;charset=utf-8`, инициирует скачивание и освобождает object URL.
- Сканированный текст никогда не попадает в `innerHTML`.

### 2.5 Зависимости

- Существующий Microsoft Fluent UI Blazor сохраняется.
- Для тестового проекта добавляются только стандартные test-зависимости xUnit.
- Новые runtime-зависимости не планируются.

## 5. Стратегия проверки

### После каждой задачи

1. Запустить узкие тесты задачи.
2. Запустить полный `dotnet test`.
3. Выполнить Release-сборку.
4. Выполнить ручную проверку изменённого вертикального среза.
5. Сверить изменения с Definition of Done и убедиться, что нет несвязанных правок.

### Аппаратные проверки

Автоматизация не доказывает корректность разрешений браузера, драйвера, параметров конкретного сканера и фактического CRLF. Поэтому T3, контрольная точка C и финальная контрольная точка требуют реального Chromium и сканера. Без них проект может быть собран, но не считается готовым к публикации.

## 6. Риски и меры

| Риск | Влияние | Мера |
|---|---|---|
| Web Serial недоступен в браузере | Высокое | Явная проверка API, целевые Chrome/Edge, ранний T3 |
| Браузер не даёт надёжное имя `COMx` | Среднее | Псевдоним пользователя, VID/PID, системный picker |
| Параметры сканера отличаются от defaults | Высокое | Полные настройки соединения и ранний тест реального устройства |
| CRLF делится между чтениями | Высокое | Stateful-парсер и TDD до подключения UI |
| UTF-8 символ разделён между byte chunks | Высокое | Streaming `TextDecoder` в JS |
| UTF-16BE кодовая единица разделена между byte chunks | Высокое | Один streaming `TextDecoder` выбранной кодировки на всё подключение |
| Повторная подписка дублирует сканы | Высокое | Явный lifecycle подписок и тест одного события |
| Последняя правка теряется при закрытии вкладки | Среднее | JS debounce с синхронным flush на `pagehide` |
| `localStorage` повреждён или переполнен | Среднее | Версия схемы, безопасная ошибка без перезаписи, видимый статус сохранения |
| Несколько одинаковых разрешённых устройств | Среднее | Не угадывать по одинаковому VID/PID, запросить ручной выбор |
| Прямой маршрут GitHub Pages возвращает 404 | Среднее | Publish-проверка base path и SPA fallback |
| Реального устройства нет в среде разработки | Среднее | Fake-источник для логики, обязательный пользовательский аппаратный чек-лист |

## 7. Параллельность

Если работа когда-либо будет выполняться параллельно, безопасно разделять только задачи после стабилизации их контрактов:

- T4 и T9 могут выполняться независимо после T1.
- После T5 задачи T6 и T10 независимы при уже утверждённых интерфейсах состояния и экспорта.
- T2 → T3 → T7 → T8 должны выполняться последовательно.
- T11 должен начинаться после стабилизации всех пользовательских потоков.
- T12 и T13 идут последовательно после T11.

Текущий план не требует привлечения дополнительных агентов.
